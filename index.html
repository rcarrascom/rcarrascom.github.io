PulseSF: a pipeline workspace for solutions consultants

I got tired of updating Salesforce one record at a time, so I fixed it for the whole team.

problem
Every week, each of us updated notes, stages and activity for every opportunity in the Salesforce web UI, one record at a time. It ate hours.
built
A desktop app on top of the Salesforce CLI. You sign in once, edit many opportunities at once, and it pushes the changes in the background. It saves a local backup before every change, so nothing gets lost, and it shows closed-won revenue for the current quarter.
result
A round of pipeline updates went from about an hour to 15 minutes or less. It's shared internally, the Solutions Consulting team uses it, and my manager named it when announcing my promotion.

Agent Live Kit: a live map of your AI agent team

When I started running Claude Code with several sub-agents, I couldn't tell what any of them was doing. So I built a way to see it.

problem
With sub-agents, the terminal is one long scroll. You can't see which agents are running right now, who handed work to whom, whether something is stuck waiting for your permission, or what happened ten minutes ago.
built
A local web page that turns Claude Code's hook events into a live map: people, the main session, each agent type and the tools they use. Working agents glow, anything waiting on you turns amber, and beams show who's using what. It adds a flow view of hand-offs, a full activity log with search and replay, and a command-line tool that sets it up for any project and checks the install with clear fixes.
design
Local only: nothing leaves your computer, and telemetry is off. No dependencies beyond Node.js, and it works on Windows, macOS and Linux. The README has an "honest limits" section: if Claude Code never calls a tool, the map leaves it dim instead of faking activity.
try it
agent-live simulate opens a demo team with no setup.

AI agents that run real incident drills

Setting up a believable demo used to take me days. Now it takes minutes.

problem
A good demo needs a realistic incident: alerts that look like the customer's tools, the right people on call, and notes that read like a real team working the problem. Building that by hand took days for every prospect.
built
Agent workflows on Claude Code and the Model Context Protocol. They read context from CRM, chat and email, send alerts in the customer's own format, check who's really on call, and post notes and acknowledgments through the incident API, so the drill looks like a team responding live. The same set builds Runbook Automation jobs, preps discovery calls, and draws diagrams and decks.
guardrail
The drill scripts refuse to run outside a sandbox account. The agents get a short menu of tested actions, never open-ended access.

Health check first, feature second

Before I write the deck, I figure out who's going to read it.

problem
Existing customers usually get pitched add-ons with generic slides. I had two customers with the same problem, alert noise paging their teams around the clock, and two very different people who'd read my recommendation.
built
A review built from six months of each customer's own data. It starts with the fixes they can make today on the plan they already pay for: escalation gaps, stale services, urgency settings. Only then does it show what the add-on adds, as today, after quick wins, with the add-on, and their own goal. For one customer I made a visual one-pager about the two engineers carrying half the pages. For the other, a written review built around the numbers their team had set as goals months earlier.
result
After the call, the customer asked for the written review so they could share it inside their team, and my account team is using it for the follow-up with their engineering leadership. On both accounts, the sales team thanked me for the approach.
lesson
Reading the champion also means noticing when you're talking to the wrong one. On one account, the person in the room wasn't going to push it internally. The numbers still did their job: they showed the real question wasn't whether we could help, but whether we fit how their operations team works. That tells the account team exactly who to bring back in, and when.
next
Both reviews end the same way: agree the baseline together, then pilot the add-on on the noisiest services. I'm turning the method into an assistant any consultant can run.

From scheduled scripts to event-driven automation

I was the first on my team to go deep on Runbook Automation.

problem
Most prospects run PowerShell or Bash on a schedule across a lot of VMs. Jobs run long, step on each other, and nobody sees the result until something breaks.
built
Jobs customers can take to production, like network-interface diagnostics followed by a guarded fix, or health checks paired with controlled restarts. Plus the questions that always come with them: self-hosted licensing, database design and user limits.
library
Six reusable jobs so far, in three look-then-fix pairs. Each one writes what it found to the incident before it touches anything.
result

Scopion: know which deals you'll actually win

A side project I'm building in public.

problem
Freelancers and consultants track deals in spreadsheets, so they never find out which discovery questions they skipped on the deals they lost.
built
A small pipeline tracker that runs offline. It keeps every deal and its next step, marks risky ones red, yellow or green, handles bulk updates and one-click briefs, and shows win rate by lead source and which qualification signals actually predict a win. Exports to CSV, JSON or Markdown, with a CRM sync prototype.
run it
./scopion.command. No database, no account, sample data only.
